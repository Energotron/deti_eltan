# TGalaxy.LoadFromStream — бинарный формат (реверс-инжиниринг)

Статус: в процессе. Цель — воспроизвести полноценную загрузку второй
галактики через штатный десериализатор игры вместо ручного вызова
отдельных конструкторов (тот путь трижды приводил к реальным крашам, см.
`CHANGELOG.md`, коммиты вокруг `CEAdapterCreateSecondDestination`).

Разбирается дизассемблером `tools/disasm_rangers.py` против установленного
`Rangers.exe` (Steam build 20648864, версия 2.1.2500.0, timestamp
`0x68eccc46`, image size `0x004d1000`). Все адреса ниже — VA для этого
конкретного билда; при пересборке DLL адаптера переводить в RVA вычитанием
`0x400000` (image base).

## Расположение

- `TGalaxy.LoadFromStream` — VA `0x0083b6cc`. Сигнатура: `eax`=self
  (`TGalaxy`), `edx`=reader-объект. Занимает огромный диапазон, минимум
  `0x83b6cc`–`0x83e920` (≈8.8 КБ машинного кода, это НЕ конец — после
  `0x83e920` идёт другая функция с одним аргументом, непохожая на
  `SaveToStream`, но и не факт что `LoadFromStream` заканчивается ровно на
  границе; нужно перепроверить).
- Стоит сразу перед ней (`0x83a1a4`–`0x83b6cc`) — судя по размеру и
  обращениям к военным/сезонным глобалам, вероятно `TGalaxy.NextDay` (тот
  самый `TGalaxy.NextDay label = N`, который постоянно фигурирует в логах
  крашей — но это generic-обёртка RScript-движка на любое исключение в
  Turn-коде, а не обязательно код именно из этой функции).
- `TGalaxy.SaveToStream` (парный писатель) пока **не найден**. Соседняя
  функция после `0x83e920` — однопараметрическая (только `eax`), строит
  форматированные строки (`call 0x7fc23c`-подобные), больше похожа на some
  `GetReport`/`GetDescription`, не на writer. Судя по всему, Save/Load не
  лежат рядом в этом классе.

## Формат reader-объекта (тот, что передаётся в `edx`)

Это НЕ полноценный класс с виртуальными методами — все read-хелперы берут
его как обычный `self` в `eax` и работают с полями напрямую (без
диспетчеризации через vtable). Значит его можно сфабриковать вручную:
достаточно куска памяти нужного размера, не обязательно настоящий Delphi
объект.

Поля (все смещения от начала объекта):

- `+0x04` (`dword`) — общий размер буфера в байтах. Используется только для
  bounds-check.
- `+0x0c` (`dword`) — текущая позиция чтения (курсор), начинается с `0`.
- `+0x10` (`dword`) — указатель на сырой байтовый буфер.

Bounds-check хелпер `0x0082ef40(self, count)`: проверяет
`self.pos + count <= self.size`; если нет — кидает Pascal-исключение
(`Error.Script`-подобная строка через `0x40dbbc`). Если бы этот путь
сработал на невалидном reader'е, это была бы штатная, перехватываемая
RScript-ошибка, а не низкоуровневый краш — совпадает с тем, что мы уже
видели для `TransferShip`.

### Примитивные read-хелперы

Все вызываются как `self=eax`, читают `N` байт с текущей позиции, двигают
курсор, возвращают значение в `eax` (int) или через FPU (`float`).

| VA | Что читает | Размер |
|---|---|---|
| `0x0082fa5c` | `byte`/`bool` | 1 |
| `0x0082f81c` | `byte`/`bool` | 1 |
| `0x0082f890` | `word` | 2 |
| `0x0082f904` | `dword`/`integer` | 4 |
| `0x0082f8cc` | `dword`/`integer` | 4 |
| `0x0082f93c` | `single` (float, через FPU `fstp`) | 4 |
| `0x0082ff18(self, out ptr)` | **строка** (см. ниже) | переменная |

Строковый ридер `0x0082ff18` → `0x0082fad4` → `0x0082faf8`: сначала читает
compact-encoded длину (переменной длины, побайтово, похоже на 7-битный
varint), затем копирует это количество байт как символы. Кодировка не
проверена (возможно однобайтовая ANSI/CP1251, т.к. игра русскоязычная).

### Версионный гейт

Глобал `[0x00882580]` (dword) читается несколько раз и сравнивается с
разными порогами (`0x65`=101, `0x7a`=122, `0x9e`=158 и т.д.) — это номер
версии формата сохранения; при старой версии соответствующий блок данных
пропускается. У нас (текущий билд) это значение стабильно и достаточно
большое, чтобы проходить все виденные гейты (не падали на них).

## Этапы (`[ebp-0x90]` = номер этапа, только для сообщений об ошибках)

Перед этапом 1 — необозначенный "заголовок": несколько bool/dword-полей
`self+0x60/0x64/0x68/0x6c/0x70/0x71` (версионные, часть под гейтом
`>= 0x65`).

### Этап 1 — звёзды (`self+0x164`)

- `word` количество, диапазон `1..10000`.
- Цикл N раз: `ctor(class=[0x838e00], addr=0x854b50)` → новая звезда;
  `Add(self.Stars=[self+0x164], star)`; затем
  `init(self=star, ecx=galaxy, edx=reader) @ 0x855224` — отдельная функция,
  ещё не разобрана детально (что именно она читает из потока для каждой
  звезды).
- После цикла: `call 0x87108c(self)` — похоже на перестройку индекса/сортировку
  списка звёзд. Затем `[0x882a7c] := 0` (сброс какого-то глобального флага).

### Этап 2 — «системы» / `TCon` (`self+0x2c`)

Это тот самый класс, который принимает `TransferShip` как валидную цель
(см. `CEAdapterCreateSecondDestination` в адаптере).

- `word` количество, диапазон `1..10000` (минимум 1 — пропустить нельзя).
- Цикл: `ctor(class=[0x838f6c], addr=0x8482f8)` → новый `TCon`;
  `Add(self+0x2c, con)`; `init(self=con, ecx=galaxy, edx=reader) @ 0x849a68`.
- `0x849a68` — это, по сути, `TCon.LoadFromStream`, полностью отдельный
  вложенный формат. **Полностью разобран**, см. отдельный раздел ниже.

### Этап 3 — неизвестный класс (`self+0x34`)

- `word` количество, диапазон `0..10000` (можно пропустить, count=0).
- Цикл: `ctor(class=[0x838d04], addr=0x8704ec)` → объект;
  `Add(self+0x34, obj)`; `init(self=obj, ecx=galaxy, edx=reader) @ 0x87065c`.
- Смысл класса не установлен (кандидат: сектора/`TCluster`, судя по
  использованию рядом с этапом 4).

### Этап 4 — похоже на планеты, привязанные к существующим `TCon`

- `call 0x842ff4(self)` — что-то готовит перед циклом (возможно, сброс
  индекса).
- `word` количество, диапазон `0..10000`.
- Цикл: **не создаёт** новый объект напрямую, а вызывает
  `0x843088(self=galaxy, edx=0)` → получает объект-мишень (`[ebp-0x3c]`),
  затем настраивает его через ВИРТУАЛЬНЫЕ вызовы (vtable), при этом читая
  поля из потока в таком порядке:
  1. `single` × 2 (X, Y) → `vtable[+0xc](x, y)` — вероятно `SetPosition`.
  2. `byte` → `vtable[+0x2c](byte)`.
  3. `word` → используется как индекс/длина для ещё одного вызова
     `0x414ea0`, затем `vtable[+0x44](...)`.
  4. `string` → `vtable[+0x34](string)` — вероятно `SetName`.
- Гипотеза: это планеты (координаты + имя), создаются через фабрику
  `0x843088`, а не через `ctor`+`Add` напрямую — не проверено.

### Этап 5 — список сырых `dword` (`self+0x38`)

- `word` количество, диапазон `1..10000`.
- Цикл: читает `dword` (`0x82f8cc`), просто добавляет как значение в
  `self+0x38` (`Add(self+0x38, value)`) — не объект, а число (возможно,
  индекс/ссылка).

### После этапа 5 — перекрёстная перелинковка

Код обходит `self+0x2c` (`TCon`-список), для каждого `TCon` смотрит его
собственный саб-список `con+0x24` (тоже список — вероятно, планеты этой
системы) и сверяет/перестраивает связи со списком `self+0x38` из этапа 5.
Логика сложная (много `GetItem`/`IndexOf`/условных веток), до конца не
прослежена — это следующий кусок для разбора.

## `TCon.LoadFromStream` (VA `0x00849a68`) — вложенный формат, разобран целиком

Сигнатура: `eax`=self (`TCon`), `ecx`=galaxy (используется дальше внутри
для регистрации в родительских списках), `edx`=тот же reader-объект, что и
у внешнего `LoadFromStream` (общий курсор — байты идут единым потоком, не
отдельными под-буферами на каждый `TCon`).

### Заголовок (всегда присутствует, без счётчика)

По порядку чтения:

1. `dword` → `self+0x04` — судя по сверке с `[context+8]` (счётчик
   следующего свободного ID) и авто-инкременту этого счётчика, это
   **уникальный ID системы**.
2. Версионный гейт `[0x882580] >= 0x9e` (158): если версия МЕНЬШЕ — читает
   ещё один `bool` (`0x82fa5c`), результат никуда не сохраняется в этой
   точке (эффект есть где-то раньше по коду, не до конца ясно). На нашем
   билде везде, где проверялась версия, порог проходился — считаем `>=0x9e`
   верным, но **не подтверждено runtime-значение** (добавлен безопасный
   `CEAdapterProbeSaveFormatVersion`, см. ниже).
3. `string` → `self+0x10` — **имя системы**.
4. `single` (float) → `self+0x14` — координата X.
5. `single` (float) → `self+0x18` — координата Y.
6. `word` → `self+0x1c`.
7. `byte` → `self+0x7c`.

### Под-этапы (все допускают `count=0`, счётчик — всегда `word`)

| Под-этап | Куда кладёт | Класс/что создаёт |
|---|---|---|
| 1 (после заголовка) | `self+0x24` | `ctor([0x76a2bc])` — тот самый второй класс, валидный как цель `TransferShip` (вероятно планеты) |
| 3 | `self+0x28` | `ctor([0x76941c]? — глобал 0x769418 читается через 0x769470)` |
| 5 | (не сохранён отдельно, только регистрируется через `0x76960c`) | не объект напрямую, регистрация через глобал `[0x769418]` |
| 7 | `self+0x30` | простое значение через `0x74f41c`/`0x74fd00` (byte-код → id) |
| 8 | (переиспользует count этапа 7) | аналогично |
| 9 | локальный alloc `0x14` байт (`0x813d74`), поля `+4`,`+8` (float X/Y), `+0xc` (dword), `+0x10` (byte=0), `+0x11` (byte) | добавляется в `self+0x34` |
| 10 | `self+0x38` | конструирует через глобал `[0x5e5554]`, версия-гейт `> 0x7f` (127) на дополнительный блок |

Каждый под-этап читает `word` count (диапазон не всегда явно
верхне-ограничен, но нижняя граница везде `0`, подтверждено
дизассемблером — `jl error` только при `count < 0`, что для `word`
никогда не бывает истинным на практике, т.е. **всегда проходит**).

### Минимальная валидная запись `TCon`

```
dword   id            (любое, лишь бы не совпадало с чужими — сверяется с context.next_id)
[bool]  — только если версия < 0x9e; на нашем билде не пишем
string  name          (длина + байты)
single  x
single  y
word    <любое>
byte    <любое>
word    0   -- под-этап 1
word    0   -- под-этап 3
word    0   -- под-этап 5
word    0   -- под-этап 7 (и 8 переиспользует)
word    0   -- под-этап 9
word    0   -- под-этап 10 (+ версионный блок пропускается, если [0x882580] <= 0x7f, что маловероятно на нашем билде — нужно подтвердить)
```

Это значит: **минимальная система = dword + string + 2×float + word + byte
+ 5×word(=0)** — компактно и полностью в наших руках (кроме course, id
уникальности и версионного бита, которые зависят от подтверждённого
`[0x882580]`).

## Обязательность этапов (по проверкам границ счётчика в потоке)

Ключевое упрощение: у части этапов проверка "count < X" кидает ошибку
только если X=1 (обязателен минимум 1 элемент), а у части допускает 0
(тогда цикл просто не выполняется — этап можно закрыть count=0, ничего
больше не читая для него).

| Этап | Мин. count | Обязателен? |
|---|---|---|
| 1 — звёзды (`self+0x164`) | 1 | Да |
| 2 — `TCon`/системы (`self+0x2c`) | 1 | Да |
| 3 — класс `[0x838d04]` (`self+0x34`) | 0 | Нет, можно пропустить |
| 4 — планеты-через-фабрику | 0 | Нет, можно пропустить |
| 5 — список `dword` (`self+0x38`) | 1 | Да, но что именно писать — не ясно (см. ниже) |
| 6 — список `dword` (`self+0x3c`) | 1 | Да, но что писать — не ясно |
| 7 — версионно-условный список (только читается и отбрасывается) | 0 | Нет |
| 8 — экономика/фракции (`0x6aaXXX`) | 0 (`jle`, не `jl`!) | Нет, можно пропустить |
| 9 — конструирует что-то через `[0x814bf4]` | — | Не читает из потока вообще, безусловный |
| 10 — обходит глобальный список `[0x882ae4]`, обнуляет поля | — | Не читает из потока, безусловный |
| после 10 — ещё один список (счётчик без верхней проверки диапазона) | 0 (похоже) | Похоже, можно пропустить |

Два простых скалярных поля читаются безусловно (не в цикле, не под
счётчиком): `self+0xc8` (`dword`) и `self+0xcc` (`dword`) — можно просто
скопировать значения с реальной галактики напрямую по тем же смещениям в
памяти, без похода через формат потока.

Вывод: реально обязательных нетривиальных этапов — **четыре**: заголовок
(простые скаляры), этап 1 (звёзды), этап 2 (системы, свои данные), и два
списка `dword` этапов 5 и 6 (нужно понять их смысл, прежде чем писать туда
случайные числа — возможно, это индексы/ссылки, которые дальше
используются в перелинковке).

## Практический вывод на сейчас

`CEAdapterCreateSecondDestination` (голый вызов конструктора `TCon` в
обход этого формата) — тупиковый путь, см. `CHANGELOG.md`: три реальных
краша подряд, включая порчу общего состояния игры даже при пойманном через
SEH-guard исключении. Второй Дом можно получить только пройдя через
`LoadFromStream` целиком (или полностью реплицировав его логику), не
обходными путями.
