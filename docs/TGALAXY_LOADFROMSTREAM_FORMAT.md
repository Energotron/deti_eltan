# TGalaxy.LoadFromStream — бинарный формат (реверс-инжиниринг)

Статус: в процессе. Цель — воспроизвести полноценное сохранение и загрузку
второй галактики через штатную пару сериализаторов игры вместо ручного вызова
отдельных конструкторов (тот путь трижды приводил к реальным крашам, см.
`CHANGELOG.md`, коммиты вокруг `CEAdapterCreateSecondDestination`).

Разбирается дизассемблером `tools/disasm_rangers.py` против установленного
`Rangers.exe` (Steam build 20648864, версия 2.1.2500.0, timestamp
`0x68eccc46`, image size `0x004d1000`). Все адреса ниже — VA для этого
конкретного билда; при пересборке DLL адаптера переводить в RVA вычитанием
`0x400000` (image base).

## Расположение

- `TGalaxy.LoadFromStream` — VA `0x0083b6cc`. Сигнатура: `eax`=self
  (`TGalaxy`), `edx`=reader-объект. Занимает огромный диапазон, минимум
  `0x83b6cc`–`0x83e920` (≈8.8 КБ машинного кода, это НЕ конец — после
  `0x83e920` идёт другая функция с одним аргументом, непохожая на
  `SaveToStream`, но и не факт что `LoadFromStream` заканчивается ровно на
  границе; нужно перепроверить).
- `TGalaxy.SaveToStream` — VA `0x0083a1a4`, непосредственно перед reader.
  Сигнатура симметрична loader: `eax`=self (`TGalaxy`), `edx`=буфер.
  Это подтверждено не соседством адресов, а полной симметрией полей и
  примитивов записи: начало пишет строку набора модов, `self+0x58`,
  `self+0x5c`, `self+0x60`, `self+0x64`, два `single`, затем те же списки,
  которые `0x83b6cc` читает обратно. Функция заканчивается в `0x83b6c1`.
- Буфер создаётся штатным конструктором VA `0x0082eab0` из class cell
  `0x0082ea5c`. Его layout совпадает с reader: `+0x04` длина, `+0x08`
  ёмкость, `+0x0c` позиция, `+0x10` указатель на байты. После записи тот же
  объект можно перемотать (`position=0`) и передать в `LoadFromStream`.
- Функция после loader (`0x83e920`) не является парным writer: парный writer
  уже однозначно найден перед loader.

## Формат reader-объекта (тот, что передаётся в `edx`)

Это НЕ полноценный класс с виртуальными методами — все read-хелперы берут
его как обычный `self` в `eax` и работают с полями напрямую (без
диспетчеризации через vtable). Значит его можно сфабриковать вручную:
достаточно куска памяти нужного размера, не обязательно настоящий Delphi
объект.

Поля (все смещения от начала объекта):

- `+0x04` (`dword`) — общий размер буфера в байтах. Используется только для
  bounds-check.
- `+0x0c` (`dword`) — текущая позиция чтения (курсор), начинается с `0`.
- `+0x10` (`dword`) — указатель на сырой байтовый буфер.

Bounds-check хелпер `0x0082ef40(self, count)`: проверяет
`self.pos + count <= self.size`; если нет — кидает Pascal-исключение
(`Error.Script`-подобная строка через `0x40dbbc`). Если бы этот путь
сработал на невалидном reader'е, это была бы штатная, перехватываемая
RScript-ошибка, а не низкоуровневый краш — совпадает с тем, что мы уже
видели для `TransferShip`.

### Примитивные read-хелперы

Все вызываются как `self=eax`, читают `N` байт с текущей позиции, двигают
курсор, возвращают значение в `eax` (int) или через FPU (`float`).

| VA | Что читает | Размер |
|---|---|---|
| `0x0082fa5c` | `byte`/`bool` | 1 |
| `0x0082f81c` | `byte`/`bool` | 1 |
| `0x0082f890` | `word` | 2 |
| `0x0082f904` | `dword`/`integer` | 4 |
| `0x0082f8cc` | `dword`/`integer` | 4 |
| `0x0082f93c` | `single` (float, через FPU `fstp`) | 4 |
| `0x0082ff18(self, out ptr)` | **строка** (см. ниже) | переменная |

**Исправлено (23 июля 2026, дизассемблировано целиком, не гадал):** строковый
ридер `0x0082ff18` → `0x0082fad4` → `0x0082faf8` — это **не** varint-длина.
`0x0082faf8(self, pos)` сканирует буфер `self+0x10` НАЧИНАЯ с позиции `pos`
`WORD`-ами (2 байта за шаг, `*(WORD*)(data+pos)` через хелперы `0x814574`
[`data+pos` — просто адрес] и `0x814600` [`*(WORD*)адрес`]), считая шаги,
пока не встретит `WORD`, равный `0` — это терминатор. Возвращает количество
символов (не байт) до терминатора.

**Строки в этом формате — это NUL-terminated UTF-16 (WideChar), а не
однобайтовая ANSI/CP1251 строка с префиксом длины.** Байтовый размер на
диске = `(число_символов + 1) * 2` (символы + один терминирующий `0x0000`).
Если бы синтез потока байт использовал старое (неверное) предположение
варинт+ANSI, первая же строка сломала бы всё сообщение — эта ошибка
исправлена ДО написания кода синтезатора, не после краша.

### Версионный гейт

Глобал `[0x00882580]` (dword) читается несколько раз и сравнивается с
разными порогами (`0x65`=101, `0x7a`=122, `0x9e`=158 и т.д.) — это номер
версии формата сохранения; при старой версии соответствующий блок данных
пропускается. У нас (текущий билд) это значение стабильно и достаточно
большое, чтобы проходить все виденные гейты (не падали на них).

## Этапы (`[ebp-0x90]` = номер этапа, только для сообщений об ошибках)

Перед этапом 1 — необозначенный "заголовок": несколько bool/dword-полей
`self+0x60/0x64/0x68/0x6c/0x70/0x71` (версионные, часть под гейтом
`>= 0x65`).

**Исправлено (23 июля 2026):** прежняя версия этого документа (пункт 16
раздела «Заголовок... уточнено») перепутала ДВА РАЗНЫХ гейта `>= 0x7f`,
идущих подряд. Дизассемблировано целиком:

1. Первый гейт `>= 0x7f`: читает `word` (или `0`, если версия меньше) —
   это count для СОВЕРШЕННО ОТДЕЛЬНОЙ структуры на `self+0xc4`, НЕ звёзды.
   Каждая запись — сырой `HeapAlloc` на `0x78` (120) байт (`byte[0]=0x44`
   ставится самим аллокатором), затем читается: строка (см. поле `+4`),
   float (`+0xc`), 8×dword (`+0x10..+0x2c`), byte (`+0x30`), dword (`+0x31`),
   byte (`+0x35`), byte (`+0x36`), опциональный byte под гейтом `>=0x84`
   (`+0x37`, иначе `=1`), 9×float (`+0x38..+0x58`), три НЕЗАВИСИМО
   опциональных строки (каждая — свой `bool`-флаг перед строкой; `+0x60`,
   `+0x64`, `+0x68`), dword (`+0x6c`), byte (`+0x70`), byte через хелпер
   `0x74fd00` (`+0x71`). Похоже на кэш/сводку по системам для UI
   (миникарта, сканер), не на сами игровые объекты. **Count=0 подтверждённо
   безопасен** — есть чёткий `dec eax; test eax,eax; jl <после-цикла>`
   перед циклом (пропущено в более раннем анализе); можно просто не писать
   ни одной записи этой структуры.
2. Сразу после — второй, отдельный гейт (без версионной проверки,
   безусловно читает `word`) — это и есть настоящий «Этап 1»: количество
   звёзд, `self+0x164`, описано ниже.

### Этап 1 — «звёзды» (`self+0x164`) — **скорее всего это сектора, не звёзды**

- `word` количество, диапазон `1..10000`.
- Цикл N раз: `ctor(class=[0x838e00], addr=0x854b50)` → новый объект;
  `Add(self.Stars=[self+0x164], obj)`; затем
  `init(self=obj, ecx=context_с_next_id, edx=reader) @ 0x855224`.

**Переоценка (23 июля 2026):** прямое сравнение на живой галактике
(`CEAdapterCompareStarConCounts`) показало `self+0x164` count = **20**,
`self+0x2c` (TCon) count = **73** — независимые списки, как и
предполагалось. Но 20 — это ТОЧНО число секторов в этой же галактике
(`GalaxySectors()`). А формат `0x855224` читает `dword` в `+0x04` (ID), но
**не читает `+0x08` из потока вообще** — ровно то поле, где живым
диффом (`SectorVisible` до/после) нашли флаг видимости сектора. Это
сильно указывает: класс, который документ называл "звёзды" (по имени
поля `self+0x164`, названному по догадке, не по факту) — на самом деле
**нативный класс секторов**, тот же самый, что отдаёт `GalaxySectors()`/
`StarToCon()`. Тогда понятно, почему запись в сектор+0x04 никогда не
влияла на отображаемое имя: имя сектора, похоже, не хранится и не
читается как строка НИГДЕ в этом формате — оно, вероятно, вычисляется по
ПОЗИЦИИ объекта в списке `self+0x164` (N-й по счёту → `Constellations.
Name[N+1]`), а не по какому-либо полю самого объекта. Раздел ниже
переименован по факту, но VA-адреса и байтовые смещения — из
дизассемблера, не переименовывались бездоказательно.

**Частично разобрано (23 июля 2026), сложнее TCon, не закончено:**

1. `dword` (`0x82f8cc`) → `star+0x04` — уникальный ID, тот же паттерн
   сверки/автоинкремента через `context+4`, что и у `TCon.LoadFromStream`.
2. `byte`/`bool` (`0x82fa5c`) → `star+0x09`.
3. `word` (`0x82f890`) → `star+0x88` (объект точно больше `0x88` байт).
4. `single` → `star+0x0c`.
5. `single` → `star+0x10`.
6. Список A: `word` count (0 безопасен) → цикл: `dword` (`0x82f8cc`) →
   `Add(star+0x18, value)` — сырые числа, не объекты.
7. Список Б: `word` count (0 безопасен) → цикл: `dword` (`0x82f8cc`) →
   `Add(star+0x1c, value)` — аналогично, другое поле.
8. Список В: `word` count (0 безопасен) → цикл: `alloc(0x1c=28 байт,
   0x402f04)` → 4×`single` (байты `+0`,`+4`,`+8`,`+0xc` нового блока) →
   `Add(star+0x20, block)`.
9. Версионный гейт `>= 0x2d` (45, всегда true на нашем билде): ещё один
   `word`-count цикл начинается сразу после — **не досмотрено до конца**,
   нужно продолжить дизассемблирование с `0x008553b6` дальше.

Похоже на существенно более насыщенный формат, чем `TCon` (несколько
списков сырых значений плюс список из 4-float блоков) — вероятно,
хранит гиперпрыжковые связи/маршруты и что-то ещё для звезды. **Работа не
закончена**: минимальная валидная запись звезды (все三 списка = `count 0`)
скорее всего безопасна по аналогии с `TCon`, но версионный гейт `>=0x2d`
и всё, что после него, ещё не проверено дизассемблером.
- После цикла: `call 0x87108c(self)` — похоже на перестройку индекса/сортировку
  списка звёзд. Затем `[0x882a7c] := 0` (сброс какого-то глобального флага).

### Этап 2 — «системы» / `TCon` (`self+0x2c`)

Это тот самый класс, который принимает `TransferShip` как валидную цель
(см. `CEAdapterCreateSecondDestination` в адаптере).

- `word` количество, диапазон `1..10000` (минимум 1 — пропустить нельзя).
- Цикл: `ctor(class=[0x838f6c], addr=0x8482f8)` → новый `TCon`;
  `Add(self+0x2c, con)`; `init(self=con, ecx=galaxy, edx=reader) @ 0x849a68`.
- `0x849a68` — это, по сути, `TCon.LoadFromStream`, полностью отдельный
  вложенный формат. **Полностью разобран**, см. отдельный раздел ниже.

### Этап 3 — неизвестный класс (`self+0x34`)

- `word` количество, диапазон `0..10000` (можно пропустить, count=0).
- Цикл: `ctor(class=[0x838d04], addr=0x8704ec)` → объект;
  `Add(self+0x34, obj)`; `init(self=obj, ecx=galaxy, edx=reader) @ 0x87065c`.
- Смысл класса не установлен (кандидат: сектора/`TCluster`, судя по
  использованию рядом с этапом 4).

### Этап 4 — похоже на планеты, привязанные к существующим `TCon`

- `call 0x842ff4(self)` — что-то готовит перед циклом (возможно, сброс
  индекса).
- `word` количество, диапазон `0..10000`.
- Цикл: **не создаёт** новый объект напрямую, а вызывает
  `0x843088(self=galaxy, edx=0)` → получает объект-мишень (`[ebp-0x3c]`),
  затем настраивает его через ВИРТУАЛЬНЫЕ вызовы (vtable), при этом читая
  поля из потока в таком порядке:
  1. `single` × 2 (X, Y) → `vtable[+0xc](x, y)` — вероятно `SetPosition`.
  2. `byte` → `vtable[+0x2c](byte)`.
  3. `word` → используется как индекс/длина для ещё одного вызова
     `0x414ea0`, затем `vtable[+0x44](...)`.
  4. `string` → `vtable[+0x34](string)` — вероятно `SetName`.
- Гипотеза: это планеты (координаты + имя), создаются через фабрику
  `0x843088`, а не через `ctor`+`Add` напрямую — не проверено.

### Этап 5 — список сырых `dword` (`self+0x38`)

- `word` количество, диапазон `1..10000`.
- Цикл: читает `dword` (`0x82f8cc`), просто добавляет как значение в
  `self+0x38` (`Add(self+0x38, value)`) — не объект, а число (возможно,
  индекс/ссылка).

### Этап 6 — список сырых `dword` (`self+0x3c`)

- `word` количество, диапазон `1..10000`.
- Цикл: читает `dword` (`0x82f8cc`), добавляет как значение в `self+0x3c`.
  Идентичная структура Этапу 5, другое поле. Не найдено, что именно её
  потребляет внутри `LoadFromStream` (возможно, потребитель — другая
  функция, вне этой; не прослеживалось дальше).

### После этапа 5 — перекрёстная перелинковка (**разобрано целиком,
23 июля 2026**)

Двойной вложенный цикл: снаружи — по каждому `TCon` в `self+0x2c`; внутри —
по каждому элементу `con+0x24` (саб-список TCon, тот же список, что и
подэтап 1 `TCon.LoadFromStream`, вероятно планеты системы). Для каждого
элемента `item`:

1. Читает `item+0x04` — **обычный маленький целочисленный ID**, не
   указатель (тот же паттерн полей, что уже видели у объектов-«секторов»
   этой сессии: последовательный номер, не индекс имени).
2. Bounds-check: `item+0x04 > count_из_этапа_5` → пропустить элемент.
3. Если в допустимом диапазоне: `GetItem(self+0x38, item.field_0x04 - 1)`
   (1-based → 0-based) и сравнивает результат С ТЕМ ЖЕ `item+0x04` ЕЩЁ РАЗ.
   То есть Этап 5 — это, по сути, таблица **самопроверки/идентичности**:
   ожидается `list_0x38[i] == i+1` для каждого `i` — просто последовательные
   числа `1..N`, используемые как ключ для сверки, а не смысловые данные.
4. При совпадении — вызывает либо `0x41645c(item)` (если проверка через
   `0x38` совпала на первом варианте сравнения), либо повторяет тот же
   паттерн ещё раз со СВОИМ отдельным локальным индексом `[ebp-0x14]`
   (перебирает `self+0x38` целиком линейным поиском в этом случае, а не по
   прямому индексу) и вызывает `0x41645c(self+0x38, item, найденный_индекс)`
   при совпадении.

**Практический вывод для синтеза минимальной галактики:** весь этот цикл
ограничен размером `con+0x24` (саб-список КАЖДОГО TCon). Если у всех
`TCon` в синтезированном потоке саб-список `con+0x24` пуст (count=0 на
подэтапе 1 `TCon.LoadFromStream` — уже часть «минимальной валидной
записи» ниже), внутренний цикл ни разу не выполнится ни для одного `TCon`,
и содержимое списков Этапов 5/6 становится **функционально неважным** —
достаточно `count=1` с любым одним `dword` (например, `1`), лишь бы
пройти обязательный минимум `count>=1`.

## Заголовок `TGalaxy.LoadFromStream` (перед этапом 1) — уточнено, оказался сложнее

Более ранняя версия этого документа недооценила заголовок. Полная
последовательность чтения от самого начала функции:

1. Версионный гейт `>= 0x65` (101): если да — читает **строку** (проверка
   набора модов на совпадение с текущим). Подтверждено по строкам рядом:
   `"Warning! Mod sets mismatch: - when this save was made you were not
   using mods"` — это чисто предупреждение в лог, **не влияет на
   структуру и не критично**; можно передать пустую строку.
2. `dword` → `self+0x58`.
3. `dword` → `self+0x5c` — **и тут же используется как count** для
   дополнительного списка `self+0xc4`: цикл создаёт `count` записей по
   `0x78` (120) байт каждая через сырой аллокатор `0x004067a0` (НЕ
   Delphi-конструктор класса, просто `HeapAlloc`-подобное выделение,
   `byte[0]=0x44`), добавляет в `self+0xc4`. **Не подтверждено, безопасен
   ли `count=0` здесь** — не видно явного `dec;test;jl skip`-паттерна
   перед этим циклом, в отличие от всех остальных счётчиков в этом
   документе. Требует отдельной проверки перед использованием нуля.
4. `dword` → `self+0x60`.
5. `dword` → `self+0x64`.
6. `single` → `self+0x68`.
7. `single` → `self+0x6c`.
8. `bool` (`0x82fa5c`) → передаётся в `0x4ba240(quest/journal-объект, bool)`.
9. `bool` (`0x82fa5c`) → передаётся в `0x4ba2c4(quest/journal-объект, bool)`.
10. Версионный гейт `== 0x88` (136, точное равенство, не диапазон): если
    да — доп. вызов `0x4ba2c4(..., 0)`.
11. Версионный гейт: `версия - 0x88`, затем ещё `-4`, затем `-2` — тройная
    проверка на три конкретных значения (`0x88`, `0x8c`, `0x8e`); если ни
    одно не совпало — доп. вызов `0x4ba240(..., 0)`. Ничего из потока не
    читает, только звонки в quest/journal-подсистему.
12. `dword` (`0x82f904`, значение отброшено сразу же).
13. `dword` (`0x82f904`) → передаётся вместе с self в `0x00847554(self, dword)`
    — сеттер, не конструктор (нет class_ref/`dl=1` паттерна).
14. `dword` → `self+0x170`.
15. `dword+1` → `self+0x174`.
16. Версионный гейт `>= 0x7f` (127): если да — читает `word` (это и есть
    количество звёзд, дальше — уже задокументированный «этап 1»); если
    нет — количество звёзд считается `0`.

На нашем билде версия = **167** (подтверждено `CEAdapterProbeSaveFormatVersion`,
стабильно на 300+ ходах) — везде проходим по «версия высокая» ветке.

## `TCon.LoadFromStream` (VA `0x00849a68`) — вложенный формат, разобран целиком

Сигнатура: `eax`=self (`TCon`), `ecx`=galaxy (используется дальше внутри
для регистрации в родительских списках), `edx`=тот же reader-объект, что и
у внешнего `LoadFromStream` (общий курсор — байты идут единым потоком, не
отдельными под-буферами на каждый `TCon`).

### Заголовок (всегда присутствует, без счётчика)

По порядку чтения:

1. `dword` → `self+0x04` — судя по сверке с `[context+8]` (счётчик
   следующего свободного ID) и авто-инкременту этого счётчика, это
   **уникальный ID системы**.
2. Версионный гейт `[0x882580] >= 0x9e` (158): если версия МЕНЬШЕ — читает
   ещё один `bool` (`0x82fa5c`), результат никуда не сохраняется в этой
   точке (эффект есть где-то раньше по коду, не до конца ясно). На нашем
   билде везде, где проверялась версия, порог проходился — считаем `>=0x9e`
   верным, но **не подтверждено runtime-значение** (добавлен безопасный
   `CEAdapterProbeSaveFormatVersion`, см. ниже).
3. `string` → `self+0x10` — **имя системы**.
4. `single` (float) → `self+0x14` — координата X.
5. `single` (float) → `self+0x18` — координата Y.
6. `word` → `self+0x1c`.
7. `byte` → `self+0x7c`.

### Под-этапы (все допускают `count=0`, счётчик — всегда `word`)

| Под-этап | Куда кладёт | Класс/что создаёт |
|---|---|---|
| 1 (после заголовка) | `self+0x24` | `ctor([0x76a2bc])` — тот самый второй класс, валидный как цель `TransferShip` (вероятно планеты) |
| 3 | `self+0x28` | `ctor([0x76941c]? — глобал 0x769418 читается через 0x769470)` |
| 5 | (не сохранён отдельно, только регистрируется через `0x76960c`) | не объект напрямую, регистрация через глобал `[0x769418]` |
| 7 | `self+0x30` | простое значение через `0x74f41c`/`0x74fd00` (byte-код → id) |
| 8 | (переиспользует count этапа 7) | аналогично |
| 9 | локальный alloc `0x14` байт (`0x813d74`), поля `+4`,`+8` (float X/Y), `+0xc` (dword), `+0x10` (byte=0), `+0x11` (byte) | добавляется в `self+0x34` |
| 10 | `self+0x38` | конструирует через глобал `[0x5e5554]`, версия-гейт `> 0x7f` (127) на дополнительный блок |

Каждый под-этап читает `word` count (диапазон не всегда явно
верхне-ограничен, но нижняя граница везде `0`, подтверждено
дизассемблером — `jl error` только при `count < 0`, что для `word`
никогда не бывает истинным на практике, т.е. **всегда проходит**).

### Минимальная валидная запись `TCon`

```
dword   id            (любое, лишь бы не совпадало с чужими — сверяется с context.next_id)
[bool]  — только если версия < 0x9e; на нашем билде не пишем
string  name          (длина + байты)
single  x
single  y
word    <любое>
byte    <любое>
word    0   -- под-этап 1
word    0   -- под-этап 3
word    0   -- под-этап 5
word    0   -- под-этап 7 (и 8 переиспользует)
word    0   -- под-этап 9
word    0   -- под-этап 10 (+ версионный блок пропускается, если [0x882580] <= 0x7f, что маловероятно на нашем билде — нужно подтвердить)
```

Это значит: **минимальная система = dword + string + 2×float + word + byte
+ 5×word(=0)** — компактно и полностью в наших руках (кроме course, id
уникальности и версионного бита, которые зависят от подтверждённого
`[0x882580]`).

## Обязательность этапов (по проверкам границ счётчика в потоке)

Ключевое упрощение: у части этапов проверка "count < X" кидает ошибку
только если X=1 (обязателен минимум 1 элемент), а у части допускает 0
(тогда цикл просто не выполняется — этап можно закрыть count=0, ничего
больше не читая для него).

| Этап | Мин. count | Обязателен? |
|---|---|---|
| 1 — звёзды (`self+0x164`) | 1 | Да |
| 2 — `TCon`/системы (`self+0x2c`) | 1 | Да |
| 3 — класс `[0x838d04]` (`self+0x34`) | 0 | Нет, можно пропустить |
| 4 — планеты-через-фабрику | 0 | Нет, можно пропустить |
| 5 — список `dword` (`self+0x38`) | 1 | Да, но что именно писать — не ясно (см. ниже) |
| 6 — список `dword` (`self+0x3c`) | 1 | Да, но что писать — не ясно |
| 7 — версионно-условный список (только читается и отбрасывается) | 0 | Нет |
| 8 — экономика/фракции (`0x6aaXXX`) | 0 (`jle`, не `jl`!) | Нет, можно пропустить |
| 9 — конструирует что-то через `[0x814bf4]` | — | Не читает из потока вообще, безусловный |
| 10 — обходит глобальный список `[0x882ae4]`, обнуляет поля | — | Не читает из потока, безусловный |
| после 10 — ещё один список (счётчик без верхней проверки диапазона) | 0 (похоже) | Похоже, можно пропустить |

Два простых скалярных поля читаются безусловно (не в цикле, не под
счётчиком): `self+0xc8` (`dword`) и `self+0xcc` (`dword`) — можно просто
скопировать значения с реальной галактики напрямую по тем же смещениям в
памяти, без похода через формат потока.

Вывод: реально обязательных нетривиальных этапов — **четыре**: заголовок
(простые скаляры), этап 1 (звёзды), этап 2 (системы, свои данные), и два
списка `dword` этапов 5 и 6 (нужно понять их смысл, прежде чем писать туда
случайные числа — возможно, это индексы/ссылки, которые дальше
используются в перелинковке).

## Практический вывод на сейчас

### Результат ABI 9 (22 июля 2026)

Вызов `TGalaxy.SaveToStream` из `Turn`-обработчика не создал файл и заблокировал
главный поток игры более чем на 20 секунд. Процесс пришлось завершить; исходное
сохранение и архивы игры не менялись. Поэтому автоматический вызов снимка из
`CE_MapSmoke` удалён. Сам экспорт оставлен только как исследовательский код и не
является доступной игровой возможностью. До следующей попытки нужно подтвердить
границу/вложенность ZL-буфера и найти нерекурсивную точку lifecycle, совпадающую
со штатным сохранением игры.

`CEAdapterCreateSecondDestination` (голый вызов конструктора `TCon` в обход
этого формата) — тупиковый путь, см. `CHANGELOG.md`: три реальных краша
подряд, включая порчу общего состояния игры даже при пойманном через
SEH-guard исключении. Штатная пара `SaveToStream`/`LoadFromStream` снимает
необходимость вручную воспроизводить весь формат. Следующий путь — sidecar
состояния рукавов плюс полный load lifecycle, а не постоянный live-swap
сырого `TGalaxy`.

### Результаты ABI 10–11 (22 июля 2026)

Нерекурсивная точка lifecycle найдена. ABI 10 ставит 6-байтовый detour на
начало штатного `TGalaxy.SaveToStream`, сначала исполняет оригинальную функцию,
а затем копирует уже заполненный буфер. В живом тесте сохранён снимок
`2 247 725` байт с `FNV-1a 2809905677`; обычный сейв после этого успешно
загрузился. Это подтверждает корректность ABI буфера и отсутствие порчи
штатного save path.

ABI 11 ставит отдельный 8-байтовый detour на `TGalaxy.LoadFromStream`. После
полного выполнения оригинального loader одноразовый callback получил валидный
список `[galaxy+0x2c]`, прочитал 73 `TCon` и детерминированно изменил их
координаты `+0x14/+0x18` с seed `1128616787`, сохранив исходные bounds
`[9,135] x [5,91]`. Карта открылась в UI, была записана в новый слот и затем
обычно загрузилась с той же геометрией без повторного преобразования. Корабль
вылетел со станции, карта приняла маршрут к соседней системе и продолжила
обрабатывать ходы.

Это доказывает, что нативное состояние карты можно менять через штатный
load/save lifecycle и сохранять в `.sav`. Результат пока является spike:
переиспользованы ванильные объекты, имена и содержимое; одновременно живущие
два рукава и обратный переход ещё не реализованы.
