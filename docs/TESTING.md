# Что прогнать перед вливанием в ствол

Ветка вливается, **когда работа проверена**, а не когда git промолчал про
конфликты. Чистое слияние непроверенной работы — основной способ сломать ствол:
две правки могут не пересекаться ни одной строкой и при этом противоречить друг
другу по смыслу.

Проверки разложены по тому, **что для них нужно**, потому что нужное есть не у
каждого. `references/tools/` не коммитится, игры на машине может не быть вовсе.
Агент, у которого нет уровня 2 или 3, обязан сказать об этом прямо — в PR и в
`docs/AGENT_COORDINATION.md`, — а не молчать о том, чего не запускал.

| Уровень | Что нужно | Когда обязателен |
|---|---|---|
| 1. Питон и данные | ничего, кроме Python 3.9+ | **всегда** |
| 2. Сборка модуля | `references/tools/`, LLVM-MinGW | при правках `tools/`, `src/`, `smoke_module/` |
| 3. Игровой smoke | установленная игра | при всём, что доезжает до `dist/` |

## Уровень 1 — без игры и без сторонних .exe

```powershell
python -m unittest discover -s tools/tests -t .
python tools/validate_content.py
```

Ожидание: `OK`, падений нет. На 2026-07-27 это **91 тест** (один пропуск —
декомпиляция настоящего `.scr`, он пропускается сам, когда под `references/`
ничего нет) и строка вида `OK: 5 factions, 10 characters, 60 missions…`.

Синтаксис PowerShell-скриптов проверяется без запуска — полезно, когда правишь
сборку, а прогнать её нечем:

```powershell
$e = $null
[System.Management.Automation.Language.Parser]::ParseFile(
    (Resolve-Path tools\build-game-smoke.ps1), [ref]$null, [ref]$e) | Out-Null
if ($e) { $e | ForEach-Object Message } else { 'PARSE OK' }
```

## Уровень 2 — сборка модуля

Нужно то, чего нет в репозитории:

- `references/tools/RScript_4.10f/RScript.exe` — единственный компилятор
  `.rson` → `.scr`;
- `references/tools/BlockParEditor_1.9/BlockParEditor.exe` — единственный, кто
  пишет бинарный BlockPar;
- LLVM-MinGW 20260407 для PE32-адаптера (`tools/build-engine-adapter.ps1`).

```powershell
.\tools\build-game-smoke.ps1
```

⚠️ `docs/BUILD_AND_INSTALL.md`, `CODEX_BOOTSTRAP_PROMPT.md` и
`MASTER_SPEC_COMPLETE.md` называют `tools/build.ps1` и `tools/install-local.ps1`
— **таких файлов нет**. Их работу делают `build-game-smoke.ps1` и
`install-game-smoke.ps1`. Не создавать одноимённые заново: получатся две
расходящиеся сборки. Переименование это или незакрытый план — вопрос в
`docs/AGENT_COORDINATION.md`.

Успех: `OK: smoke module built at …\dist\ChildrenOfEltan`. Скрипт сам зовёт
`game_smoke_check.py preflight`, так что отдельно его гонять не нужно.

Что проверить глазами после правок сборки:

- `dist\ChildrenOfEltan\CFG\Main.dat`, `CFG\CacheData.dat`, `CFG\Rus\Lang.dat` —
  все три на месте и непустые;
- `CFG\Rus\CE_MapSmoke.txt` — на месте и **не** превратился в `.dat` (его пишет
  RScript, и он не является BlockPar-источником);
- `DATA\Script\CE_MapSmoke.scr` — свежий и меньше 64 КиБ;
- `ModuleInfo.txt` — UTF-16LE с BOM.

## Уровень 3 — игровой smoke

Нужна установленная игра. Сначала всегда сухой прогон:

```powershell
.\tools\install-game-smoke.ps1 -GameRoot '<каталог Space Rangers HD>'
```

Он пересобирает модуль и печатает source/target, ничего не трогая. Затем:

```powershell
.\tools\install-game-smoke.ps1 -GameRoot '<каталог игры>' -Install
```

Копирует `dist\ChildrenOfEltan` в `<игра>\Mods\ChildrenOfEltan` и **отказывается
перезаписывать** уже существующий каталог — перед повторной установкой старый
удалить руками.

Дальше по `docs/09_TEST_PLAN.md`, секция Smoke:

1. сохранить копию `%USERPROFILE%\Documents\SpaceRangersHD\Save`;
2. включить «Дети Эльтан» в списке модулей (модуль ставится **выключенным**);
3. запустить игру **через лаунчер мода** — иначе адаптер не инжектится;
4. создать новую партию, сохранить, выйти, загрузить;
5. проверить `%USERPROFILE%\Documents\SpaceRangersHD\########.log` и каталог
   `Errors` на строки `CE_`.

Снимок логов до и разбор после:

```powershell
python tools/game_smoke_check.py snapshot
# ... играем ...
python tools/game_smoke_check.py report
```

## ⚠️ `.dat` нельзя сравнивать побайтово

BlockParEditor **не детерминирован по байтам**: один и тот же `.txt`, дважды
прогнанный одной и той же командой, даёт `.dat` разного содержимого при
одинаковом размере (проверено на `Main`, `Lang`, `CacheData`). Внутри, судя по
всему, есть seed.

Поэтому `cmp`/`fc` по `.dat` бессмысленны, а расхождение байт — **не**
регрессия. Сравнивать так:

1. размер — должен совпадать;
2. содержимое — раскодировать оба `.dat` обратно в `.txt` тем же редактором и
   сравнить **текст**:

```powershell
python tools\srblockpar.py <старый>.dat old.txt
python tools\srblockpar.py <новый>.dat new.txt
fc /b old.txt new.txt
```

## Что проверено и что нет по батчу BlockPar (2026-07-27)

Батч-вызов в `tools/build-game-smoke.ps1` (три ручных вызова заменены одним)
прогнан **на настоящем `BlockParEditor.exe`** и настоящих исходниках мода,
A/B против старого пути:

- старый путь (три явных вызова с явным dest) и новый (стажирование + батч +
  перенос) дают `.dat` **одинакового размера** — 3208 / 3769 / 209 Б для
  `Main` / `Lang` / `CacheData`;
- раскодированные обратно в текст, все три **совпадают побайтово** между старым
  и новым путём;
- байты самих `.dat` расходятся — но ровно так же они расходятся между двумя
  прогонами **старого** пути, см. выше;
- блок PowerShell из билда прогнан целиком с настоящим редактором:
  стажирование, батч по дереву с `Rus\`, перенос трёх `.dat` в `CFG\`, уборка
  временного дерева, `CE_MapSmoke.txt` не тронут.

**Осталось непроверенным:** сборка целиком (`build-game-smoke.ps1` от начала до
конца — RScript, engine-adapter, ранний лаунчер) и всё, что дальше по уровню 3.
В этой среде нет ни игры, ни `references/tools/`; `BlockParEditor.exe` был взят
из соседнего рабочего каталога.
