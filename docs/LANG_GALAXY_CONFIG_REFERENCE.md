# Lang.dat: структура разделов, влияющих на генерацию галактики

Всё ниже получено расшифровкой **реального** `CFG/Rus/Lang.dat` установленной игры
через `references/tools/BlockParEditor_1.9/BlockParEditor.exe --cli --convert`
(2.4 МБ текста, кодировка CP1251), а не по документации и не по аналогии.
Формат разделов проверялся ещё и по рабочему стороннему моду
`Mods/Reflection/RefABitMoreStars`, который меняет число систем.

## Как расшифровать самому

```bash
BlockParEditor.exe --cli --convert <путь к Lang.dat>
```

Файл рядом с исходным, `.txt`, в CP1251. Работает и на ванильном `Lang.dat`,
и на собранном моде — то есть результат сборки можно проверять, а не угадывать.

## Кодировка (важно)

`Lang.dat` — CP1251. Исходники мода в репозитории лежат в UTF-8, поэтому
`tools/build-game-smoke.ps1` обязан перекодировать их при сборке. Раньше
`CE_MapSmoke.Lang.txt` копировался сырыми байтами (`ReadAllBytes`) — UTF-8
уезжал в движок как есть, и все кириллические имена приходили мохнатым
мусором вида «РРССРРЁ». Исправлено: файл читается как UTF-8 и
перекодируется в CP1251, как это уже делалось для `CE_InterarmTransit.Lang.txt`.

## Constellations — секторы и размеры галактики

```
Constellations ^{
    GalaxyCountStars=146
    GalaxySizeX=198
    GalaxySizeY=141
    Name ^{
        1=Гурт
        ...
        20=Дицея
    }
}
```

- В ванили ровно **20** записей `Name`, индексы с 1.
- `GalaxyCountStars` — число систем, по умолчанию 73. Это то же поле, которое
  движок читает из `[galaxy+0x160]` (подтверждено дизассемблированием
  `TGalaxy.GenerateStars`: при значении <= 0 цикл создания пропускается).
- `GalaxySizeX`/`GalaxySizeY` — размер галакарты, по умолчанию 140x100.
  Применяется только при генерации НОВОЙ галактики и автоматически
  растягивает границы существующих секторов.

### Число секторов не настраивается — закрытый вопрос

Добавление записей `Name` с индексами 21+ количество секторов НЕ увеличивает:
движок по-прежнему строит 20, просто более крупных.

Причина найдена в функции чтения конфига галактики (VA `0x007DC5C0`). Она
последовательно запрашивает ключи и подставляет дефолт, если ключа нет:

| Ключ | VA дефолта | Дефолт |
|---|---|---|
| `Constellations.GalaxyCountStars` | `0x007DC607` | `0x49` = 73 |
| `Constellations.GalaxySizeY` | `0x007DC649` | `0x64` = 100 |
| `Constellations.GalaxySizeX` | `0x007DC68B` | `0x91` = **145** |

Дальше функция переходит к `GalaxyNews.*`. Ключа для числа секторов в секции
`Constellations` нет вообще — значение 20 зашито в движке.

Отсюда два следствия. Во-первых, документация в `Script functions list.txt`
ошибается насчёт ширины: дефолт `GalaxySizeX` равен 145, а не 140, и
пропорцию надо считать от него. Во-вторых, эльтанскую половину не нужно
делать новыми секторами: карта уже вдвое больше, а её 20 секторов растянуты,
поэтому достаточно объявить дальнюю их часть эльтанской и переименовать
существующим механизмом (`ce_sector_name_helper`). Патчить движок ради
дополнительных секторов не требуется.

## Star — имена систем

```
Star ^{
    00=Тарон,Star.Normal
    01=Пхедок,Star.Normal
    02=Солнце,Star.Small
    ...
    72=<последняя ванильная>
}
```

- Записи лежат в `Star` **напрямую**, без вложенного блока `Name`.
- Индексы **с нуля**, в ванили двузначные с ведущим нулём (`00`..`72` = 73 имени).
- У каждой записи обязателен второй элемент — тип звезды: `Star.Normal` или
  `Star.Small`.
- Мод добавляет имена, продолжая нумерацию: для `GalaxyCountStars=N` нужны
  индексы `0..N-1` без пропусков.

Типичная ошибка (совершена в этом проекте): завернуть имена в
`Star ^{ Name ^{ 74=… } }` по аналогии с секторами и начать с 74. Движок такой
блок не читает вообще.

## PlanetName — имена планет

Раздел разбит на **подсекции по расам**, а не плоский список:

```
PlanetName ^{
    Fei ^{
        01=Умий
        02=Эйпентак
        ...
    }
    ...
}
```

679 строк в ванили. Имена планет — одиночные выдуманные слова, сильно разной
длины, изредка через дефис.

## RuinName — имена станций и баз

Тоже разбит на **подсекции по типам** объектов:

```
RuinName ^{
    BK ^{
        1=Эконом
        10=Высокой активности
        11=Толстяк
        ...
    }
    ...
}
```

350 строк в ванили. Индексы без ведущих нулей. Имена смешанные: одиночные
слова («Толстяк», «Магнат») и словосочетания («Красный барон»).

## Как это соотносится с планами мода

Пулы имён из конфига раздаются движком случайно по всей галактике — привязать
«наши» имена только к дальней половине через конфиг нельзя. Для этого в проекте
уже есть работающий механизм переименования в живой памяти
(`tools/native/ce_sector_name_helper.c` плюс пулы `g_ce_second_planet_names` и
`g_ce_second_station_names` в адаптере). Правильный порядок: конфигом добиться
нужного числа систем и секторов, затем переименовать дальнюю половину.

## Где в коде создаются системы (найдено) и секторы (пока нет)

Подтверждено дампом `savemergedcfg`: в слитом конфиге, который реально получает
движок, лежат **все 44** записи `Constellations.Name` вместе с
`GalaxyCountStars=146`, `GalaxySizeX=198`, `GalaxySizeY=141`. То есть мердж
исправен и формат наш верный — ограничение в 20 секторов сидит в коде.

### Цепочка от конфига до генерации

Значения из конфига кладутся в глобалы, а те читаются через ячейки-указатели:

| Что | Глобал | Ячейка | Потребители |
|---|---|---|---|
| GalaxyCountStars | `0x0087C26C` | `0x00882F10` | `0x005D432E`, `0x0065EF5E` |
| GalaxySizeY | `0x0087C270` | `0x008823E4` | `0x005D4715`, `0x005D47EE`, `0x005D4B52`, … |
| GalaxySizeX | `0x0087C274` | `0x008828C4` | `0x005D46AB`, `0x005D4784`, `0x005D4B41`, … |

### Цикл создания систем — найден

VA `0x005D432D`, внутри `TThreadCreateNewGame.Execute`:

```
mov  eax, [0x882f10]      ; ячейка GalaxyCountStars
mov  eax, [eax]           ; = 146
test eax, eax
jle  0x005D436B           ; при <= 0 генерация систем пропускается
mov  [ebp-0x7c], eax      ; граница цикла = число систем из конфига
...
mov  eax, [0x838f6c]      ; class-ref TCon
call 0x008482F8           ; конструктор TCon
mov  eax, [0x88263c]; mov eax,[eax]; mov eax,[eax+0x2c]   ; список СИСТЕМ
```

Конструктор `TCon` (`0x008482F8`) вызывается во всём экзешнике всего из двух
мест: отсюда и из `0x0083BD4A`. Это окончательно подтверждает семантику
смещений: `+0x2c` — список систем, `+0x164` — список секторов.

### Секторы — открытый вопрос

Прямо перед циклом систем, на VA `0x005D430D`, вызывается
`TGalaxy.Initialize` (`0x0083A034`) — наиболее вероятное место создания
секторов. Внутри он вызывает `0x0085861C`, тот — `0x008588B4` (трижды) и
`0x00858920`. Явной константы 20 в этой цепочке пока не найдено.

Что уже проверено и исключено:
- конфигом число секторов не задаётся (полный перебор строк экзешника:
  ключей `Constellations.*` ровно три);
- длина списка `Constellations.Name` на него не влияет (44 записи доходят,
  секторов всё равно 20).

Следующий шаг: обращений к `+0x164` в экзешнике 182 штуки — надо сузить до тех,
что пишут в список (Add), а не читают, и найти границу их цикла. Патч затем
кладётся в `CESecondMapAdapter.dll` и обязан ставиться ДО генерации, то есть
через ранний лаунчер (`tools/native/ce_early_launcher.c`), иначе не успеет.

## Секторы всё-таки добавляемы — но через сохранение, а не конфиг

Пользователь принёс `ranger-tools` (распакован в `references/ranger-tools/`,
в git не коммитится). Там лежит полный разбор формата `.sav`:
`rangers/sav.py`, ~1500 строк, с конвертацией сейв <-> JSON в обе стороны.

Ключевое из определения галактики:

```python
cons=List(TConstellation, UInt16),
stars=List(TStar, UInt16),
planets=List(ID, UInt16),
```

Секторы хранятся списком с 16-битной длиной. **Ограничения в 20 в формате
сохранения нет.** Двадцатка, которую не удалось обойти конфигом и которая
зашита в генераторе, относится только к генерации новой галактики.

Готовый пример: `modding-tools/sav/patch_galaxy_big/run.py` создаёт новые
секторы, системы и планеты прямо в сейве (`NEW_CONS = 50`), заполняя все
поля `TConstellation`, `TStar` и `TPlanet`.

Практический вывод для мода: не нужно ни патчить генератор, ни бороться с
константой 20. Достаточно сгенерировать партию штатно, а затем **дописать в
её сохранение** сектора и системы Второго Дома с нашими названиями. Тот же
инструмент решает и перенос капитана: игрок в сейве — обычная структура,
поэтому корабль, снаряжение и трюм переносятся редактированием файла, а не
через скриптовые сеттеры.

Это снимает прежнее возражение «править .sav дорого, придётся реверсить
формат» — формат уже отреверсен и покрыт рабочим кодом.
